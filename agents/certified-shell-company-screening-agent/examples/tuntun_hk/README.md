# Tuntun HK Example

This is an example case, not the whole project.

- Framework: certified shell company screening workflow.
- Market adapter: HK.
- Case: Tuntun Health HK listed-company restructuring / shell-company screening example.

## Inputs

- `input/case_input.md`
- `input/source_map.md`
- `input/transaction_boundary.md`
- `case_config.yaml`

## Trace outputs

Trace artifacts are under `trace/`, including universe, hard filter, ER/BRB, DD evidence, risk matrix, calculations, claim-to-evidence and human review.

## PCE audit outputs

PCE audit artifacts are under `pce_audit/`.

Current demo result is intentionally conservative and scoped:

- `certification_status`: `Certified with Caveat`
- `final_delivery_allowed`: `true`
- This is **scoped external-final delivery**, not full-trace certification.
- External-final delivery is allowed only for material `CLM-*` claims that are explicitly referenced in the delivery files, exist in both `claim_to_evidence_map.csv` and `pce_audit_current_run.csv`, have `delivery_scope = external_final`, and have PCE status `Certified` or `Certified with Caveat`.
- The current mapped final delivery references only `Certified` external-final `CLM-*` claims.
- Large numbers of trace rows still remain `Needs Human Review` or `Internal Trace Only`.
- Most trace artifacts remain `imported_from_original_bundle` + `pipeline_validated`; they are not represented as fully regenerated by the current pipeline.
- Content not covered by explicit external-final `CLM-*` claim mapping must remain internal limitation / process context and must not be used as final external conclusions.
- Upstream human-review / evidence-gap obligations from hard filter, ER/BRB, DD evidence, and risk matrix are propagated into PCE instead of being washed into `Certified`.

## Delivery outputs

Delivery materials are under `delivery/`. Final delivery must follow the PCE status and caveats.

## How to run

```bash
python scripts/run_tuntun_hk_demo.py
```

This validates the imported trace, replays supported calculations, runs PCE certification logic, updates delivery readiness, and writes a run record.

## Run records

Each run creates `run_records/<run_id>/` containing at least:

- `run_summary.json`
- `trace_manifest.json`
- `pce_summary.json`
- `delivery_gate_summary.json`
- `warnings.md`

These files record which configs and inputs were used, which artifacts were generated vs validated vs imported, how many PCE rows landed in each status, and whether final delivery is allowed or blocked.

This example is for research workflow prototyping only and is not investment, legal, tax, regulatory, financial, or transaction advice.
